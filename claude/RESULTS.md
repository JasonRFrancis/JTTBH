## 2. Schema Issues Noticed

### Issue 1: `book` table foreign key references `users` (plural) -- schema.sql line ~152

```sql
CONSTRAINT `books_ibfk_1` FOREIGN KEY (`userID`) REFERENCES `users` (`userID`) ON DELETE CASCADE
```

The actual table is named `user` (singular), not `users`. This foreign key
constraint will fail on table creation. The constraint body in schema.sql must
be corrected to `REFERENCES \`user\` (\`userID\`)`.

**Recommendation:** Fix schema.sql line ~152. The `book` table will not be
created correctly until this is addressed.

### Issue 2: `book` table has UNIQUE KEY on `bookID` -- incompatible with insert-only pattern

```sql
UNIQUE KEY `bookID` (`bookID`)
```

The insert-only pattern requires multiple rows per `bookID`. The UNIQUE
constraint means only one row can exist per `bookID`, making updates and
"deletes" impossible via the intended pattern. The unique key should be
removed and replaced with a plain index: `KEY idx_bookID (bookID)`.

**Recommendation:** Remove `UNIQUE KEY` on `bookID` in the `book` table.
The `book` routes in this implementation use INSERT for updates assuming
the constraint will be fixed.

### Issue 3: `podcast.created_by` is `INT` but should be `varchar(36)` (UUID)

```sql
`created_by` int NOT NULL,
```

All other tables use `created_by varchar(36)` to store the UUID of the
creating user. The `podcast` table uses `int` which would store a numeric
rowid, not a UUID. This is inconsistent and would break the standard
`created_by = %s` (user UUID) pattern used everywhere.

**Recommendation:** Change `podcast.created_by` to `varchar(36)`.

### Issue 4: `vacation` table lacks a `vacationID` UUID column

All other primary entity tables use a UUID `<entity>ID` column for stable
external references (e.g. `projectID`, `bookmarkID`). The `vacation` table
only has an auto-increment `id` column. This means vacations can only be
referenced by their integer primary key, which exposes internal structure
in URLs and makes future insert-only upgrades harder.

**Recommendation:** Add `vacationID varchar(36) NOT NULL` to the `vacation`
table and generate UUIDs on insert.

### Issue 5: `log` table uses `userid` (lowercase) not `userID` (camelCase)

```sql
`userid` varchar(36),
```

All other tables use `userID`. The `log` table uses `userid` (all lowercase).
The `__init__.py` after_request hook uses `user_id` and `method`/`path`/
`status_code`/`ip_address` column names which do not match the actual `log`
table schema (which has `userid`, `username`, `area`, `resource`, etc.).
The after_request hook will fail with a SQL error because the column names
it references do not exist.

**Recommendation:** Either update the `log` table schema to add the columns
the after_request hook expects (`method`, `path`, `status_code`, `ip_address`,
`created_at`), or update the after_request hook SQL to match the existing
columns. The existing `log` table appears to be a legacy schema from an older
version of the application.

### Issue 6: `podcast_episode` has a typo: `epidsodeID` (not `episodeID`)

```sql
`epidsodeID` varchar(36) NOT NULL,
```

Similarly, `podcast_listItem` has `epidsoeID` (missing 'i').

**Recommendation:** Fix both column names in schema.sql. The podcast.py route
works around this with aliasing (`pe.epidsodeID AS episodeID`) and explicit
column references, but the typos should be corrected.

## 3. Insert-Only Pattern Clarifications

### Project table: `name` is NOT NULL in schema, but insert-only delete requires NULL

The project.py `delete` route inserts a row with `name=NULL` to soft-delete
(the standard insert-only sentinel). However, the `project` table schema
defines `name varchar(255) ... NOT NULL`. This will cause the delete INSERT
to fail with a MySQL NOT NULL constraint violation.

**Resolution needed:** Either:
a. Change `project.name` to allow NULL: `name varchar(255) COLLATE ... DEFAULT NULL`
b. Use a separate `deleted` boolean column for the sentinel

The same issue affects `project_resource.name`.

**Recommendation:** Update `project.name` and `project_resource.name` to
allow NULL, consistent with the insert-only pattern used by the `todo` table
(`title` is NOT NULL in schema but the model inserts NULL for deletes -- this
same conflict exists in `todo` and should be verified).

### Book table: no NULL-sentinel delete possible

The `book` table has `title varchar(500) NOT NULL`. The spec does not explicitly
state that books use the NULL-sentinel delete pattern (unlike todos and projects).
The `book.py` implementation uses `status='dismiss'` to hide a book from active
views, which is the most natural pattern for books (they have a status enum).

**Recommendation:** Clarify in SPECIFICATION.md whether book soft-delete uses
`status='dismiss'` or a NULL title. The dismiss status approach is recommended.

## 4. Spec Ambiguities and Line References

### SPECIFICATION.md line ~193: Weekly list blank slots

> "The weekly list begins with 11 blank list items; custom lists begin with 5"

Implemented as `DAILY_BLANK_SLOTS = 11` and `CUSTOM_BLANK_SLOTS = 5` in
`routes/todo.py`. The `blank_slots` value passed to the template is
`max(N - len(todos), 1)` to always show at least one empty slot.

The specification does not clarify whether blank slots are rendered as empty
`<input>` elements (for immediate data entry) or as visual placeholders.
The implementation passes the count to the template for JS enhancement.

### Vacation blueprint permission: which PERM_* bit?

The `vacation` table is related to habits (vacation_mode on habit table).
No `PERM_VACATION` constant exists in `decorators.py`. The `vacation.py`
blueprint uses `PERM_HABIT` (32) as the required permission bit since
vacation management is conceptually part of habit tracking.

**Recommendation:** Either add `PERM_VACATION` or explicitly document in
SPECIFICATION.md that vacation uses the habit permission bit.

### Chore blueprint: no userID on `chore` table

The `chore` table has no `userID` column. Chores are shared within households.
The `chore.py` blueprint looks up the user's household via `household_member`
before querying chores. This means users without a household see an empty
chore page with a helpful message.

**Recommendation:** Document the household membership requirement in
SPECIFICATION.md for the chore feature.

### Journal answer insert-only: no current-state query defined

The journal feature inserts a new row for each saved answer (journal_answer).
The spec does not define a "current state" query for answers (equivalent to
the `MAX(id)` pattern used in todos and projects). The implementation uses
`MAX(ja2.id)` per `(userID, questionID, answered)` tuple to determine the
current answer for a given question+date.

**Recommendation:** Add the current-state query to SPECIFICATION.md for
journal_answer.

### `OAUTHLIB_INSECURE_TRANSPORT` flag

The `DevelopmentConfig` sets `OAUTHLIB_INSECURE_TRANSPORT = True` to allow
Google OAuth over plain HTTP in development. This flag must be `False` or
absent in production (HTTPS only). Confirmed handled in `__init__.py`
`_load_config()`.

### Podcast RSS feed public access

The `podcast.feed_xml` route is mounted under `/<username>/podcast/feed/<feed_id>.xml`
via the blueprint prefix. It does not require authentication. The route validates
that the `feed_id` belongs to the `username` in the URL to prevent enumeration.

Since the blueprint is mounted at `/<username>/podcast`, the full URL is:
`/jason/podcast/feed/<feed_id>.xml`. This is publicly accessible to any
podcast app.

### Appointment public booking page `/book/<url>`

The spec mentions a public booking page at `/book/<url>`. Since the appointment
blueprint is mounted at `/<username>/appointment`, there is no clean way to
expose `/book/<url>` from this blueprint without a separate registration.

**Recommendation:** Register a second URL prefix for appointment booking, e.g.:
```python
app.register_blueprint(appointment_bp, url_prefix='/book', name='appointment_public')
```
Or create a separate `booking.py` blueprint at the app level.

## 5. Implementation Decisions

### Bookmark deletion approach

The spec's insert-only pattern does not cleanly apply to bookmarks because:
- `url` is `TEXT NOT NULL` (no NULL sentinel for deletion)
- Each bookmark row represents a unique saved URL (not a versioned entity)

Decision: Bookmarks are not soft-deleted via insert-only. The `mark_read`
route uses a direct `UPDATE` to set `read=1`. This is the one exception to
the insert-only rule in the implementation, justified because bookmarks are
event records rather than versioned entities.

### Mood "default" category

When a user has no mood categories configured, the journal index shows a
simple "Overall Mood" fieldset with Happy/Sad radio buttons. The form field
name is `mood_default`, which won't match any category UUID in the database.
The `save_mood` route will attempt to insert a row with `categoryID='default'`.

**Recommendation:** Either create a system-level default category on user
approval, or add a guard in `save_mood` to skip the default field when no
real categories exist.

### Book update: UNIQUE KEY conflict

The `book.update` and `book.finish` routes insert new rows per the insert-only
pattern. This will fail until the `UNIQUE KEY bookID` constraint is removed
from the `book` table (see Schema Issue 2 above).

### Fitness blueprint: day-of-week conversion

Python `date.weekday()` returns Mon=0, Sun=6. The fitness schema uses
`day_of_week` as 0=Sunday, 1=Monday, ..., 6=Saturday. The conversion in
`fitness.py` is: `day_of_week = (today.weekday() + 1) % 7`.

### Chore bitmask: season not filtered in today's chore query

The `chore_listItemDay` query in `chore.py` filters by `day_of_week` bitmask
but not by `season`. Season filtering would require determining the current
season from the date and applying the season bitmask. This is deferred.

**Recommendation:** Add season detection utility (spring: Mar-May, summer:
Jun-Aug, fall: Sep-Nov, winter: Dec-Feb) and apply the season bitmask filter.

## 6. Concurrency Note

The push-forward logic in `todo.py` is not protected by a database lock.
Two simultaneous requests for the same user+date could both detect that
push-forward has not been run yet (no row in `todo_pushedForward`) and both
execute the push. This results in duplicate today entries for the affected
todos. As documented in the spec, this is by design: the insert-only pattern
is resilient to concurrency since no data is lost, just duplicated.

The current-state query (`MAX(id) per todoID`) will always return one row,
so the duplicated push records are harmless from a display perspective but
may inflate the `todo_pushedForward` table.
